# ice-climber — design document

Living design doc for `iceclimber`, a Go CLI for operating a Claude agent running in YOLO mode inside a sandbox it can't otherwise provision (Python, packages, web access), over an SSH-only link, with zero assumptions about the sandbox's shell or installed tooling.

Status: **v1 + post-v1 increments complete and verified end-to-end** against a real Alpine/musl sandbox (all §12 phases ✅, decisions #44–#61). Shipped on top of v1: **three languages** — Python/pip, JavaScript/npm, Java/Maven, each with runtime + packages over Tier 0 (mirror) and Tier 1 (relay) — and the **TUI-first operator console** (Phases 1+2). The pre-fleet hardening pass (#54) closed the console error-visibility gaps and the `sandbox_id` namespacing invariant is now tested. The `ExecFS` bulk-transfer (decision #55) shipped too — a runtime tree now pushes in one `tar` exec, so all three languages install over either transport (no SFTP-only constraint). `iceclimber trust` (decision #56) brings SSH host-key recording in-CLI (with a console first-connect modal) so onboarding an ephemeral sandbox no longer needs an out-of-band `ssh-keyscan`. `iceclimber agent install claude` (decision #57) relays a coding agent + its subscription auth into the (air-gapped) sandbox and drops a `$ICECLIMBER_HOME/nana` launcher (#58) the operator runs to start it, NANA.md wired in as system context. The demo dogfoods `nana`. (Also fixed: `web.fetch` blobs at the spec'd `protocol/blobs/` — #59.) The agent now talks to Popo via a relayed `popo` client (decision #61) that owns the protocol ceremony, shrinking NANA.md to a minimal system-prompt contract (file-I/O-only preserved as a PROTOCOL.md fallback). Remaining work: **multi-sandbox** (the fleet — Phase 3) and the v2 backlog (sub-agent/`web.research`, Tier 2 build). No open v1 polish items.

## 0. Scope — the v1 line

The design below is kept in full; it is **not** all v1. To honor "ship the minimum that solves the problem," v1 is cut as tightly as it can be while still being a real tool, and the rest is parked as **v2** — designed enough not to be re-derived later, explicitly out of the first build. Every parked item names its own re-entry trigger ("build this when X actually happens"), so v2 is demand-driven, not speculative.

- *(post-v1)* acceptance demo (phase 8, [`DEMO.md`](./DEMO.md)) + **observability**: a host activity log and `iceclimber logs` two-tail (`[POPO]`/`[NANA]`) viewer

## 1. Naming

One Go binary, two roles, named after the two Ice Climbers:

- **Popo** — the controller. Runs *outside* the sandbox (confirmed: typically on a laptop, fully outside the corporate network the sandbox sits in). Owns the SSH/SFTP connection, the deterministic dispatcher, the sub-agent fallback, the local package cache.
- **Nana** — the sandbox-side role. Not necessarily a running process — primarily a persona + skill document (`NANA.md`) that the Claude agent follows using whatever tools its own harness already gives it. An *optional* helper binary (`iceclimber nana ...`) can be pushed in as a convenience once Popo confirms the sandbox can execute one, but nothing in the system depends on it existing.

Functional CLI verbs stay plain and unambiguous (`bootstrap`, `serve`, `install`, ...). The Popo/Nana flavor lives in log lines and status output, not in command names.

## 2. Architecture overview

```
 Public internet                              Internal mirror (Artifactory/Nexus/etc.)
        |                                                    |
        v                                                    v
+--------------------------+                    +--------------------------+
| Popo (controller)        |   SSH / SFTP        | Nana (sandbox)           |
|  - package cache         | <==== requests ==== |  - outbox / inbox        |
|  - sub-agent fallback    | ====  results  ====>|    (maildir-style)       |
+--------------------------+                    |  - runtime tree           |
                                                  +--------------------------+
```

- Popo can reach the public internet but **not** the internal mirror (it sits outside the corporate network).
- The sandbox can reach the internal mirror and other company-approved endpoints directly, but has no general internet egress and no way to fetch/install anything itself.
- Requests flow sandbox → controller via `outbox`; results flow controller → sandbox via `inbox`. Both directions ride the same SSH connection.

### Key architectural decision: no daemon required inside the sandbox

The protocol only requires Nana to have *some* file read/write capability — true of essentially any code-capable agent harness. Popo does all polling via its own SSH session (SFTP or exec, see §6). A binary inside the sandbox is a convenience, never load-bearing.

**Scoping boundary (explicit):** actually *running* installed software still requires Nana's harness to expose some execution primitive that resolves paths against the same filesystem Popo populates. If a harness only exposes a fully isolated "run code" tool unconnected to that filesystem, no installation strategy on Popo's side can fix that — that's a harness limitation outside this project's scope, not a bug to work around.

### Not a real chroot

No privileged operations are assumed. The "chrootable" instinct is implemented as a self-contained, relocatable prefix tree (closer to Homebrew/pyenv than `chroot(2)`), addressed by **absolute paths**, not PATH/profile-file modification — non-interactive exec per tool-call means we can't rely on `.bashrc`/`.profile` being sourced, and we don't know which shell (if any specific one) is in play.

## 3. Directory layout

### Sandbox side (`$ICECLIMBER_HOME`, chosen during bootstrap, see §7)

```
$ICECLIMBER_HOME/
  protocol/
    outbox/
      tmp/            # Nana writes here first
      new/            # atomic rename in — Popo watches this
      cur/            # Popo renames here on pickup (rename = lock)
    inbox/
      tmp/            # Popo writes here first
      new/            # atomic rename in — Nana watches this
      cur/            # Nana renames here after consuming
    blobs/
      <sha256>        # content-addressed: wheels, fetch bodies, python tarball contents
    heartbeat         # Popo writes current timestamp as CONTENT (not mtime — see §6)
    capabilities.json # sandbox self-report, CONTROLLER-written (host + agent identity; see decision #72)
    .popo.lock        # held by `serve` for the duration of the session
  popo                # the sandbox client (relayed at bootstrap; `popo <verb>` — #61)
  runtimes/
    python/
      3.12.6-x86_64-glibc/
        bin/python3   # absolute-path contract — canonical address for invocation
  state/
    manifest.json     # convenience copy; Popo's local copy is authoritative
    pip.conf          # generated at bootstrap, index-url -> internal mirror if configured
  skill/
    NANA.md           # minimal contract (defaults the agent to `popo`)
    PROTOCOL.md       # raw file protocol — the file-I/O-only fallback (no-exec harnesses)
```

Request/response filenames are `<ulid>.json` — ULIDs sort lexically by creation time, so "what's oldest in the queue" is a plain directory listing, no per-file parsing required.

### Controller side (operator-owned, never written by Nana)

```yaml
# iceclimber.yaml
sandbox_id: my-sandbox-1
ssh: { host: ..., user: ..., identity_file: ... }
remote_root: /home/agent/.iceclimber     # confirmed/auto-set during probe

network:
  allowed_domains:
    - pattern: "artifactory.corp.internal"
      reachable_from: sandbox
      role: package_mirror               # -> pip.conf index-url points here
    - pattern: "docs.corp.internal"
      reachable_from: sandbox
  # Controller-venue fetches are gated, not allow_and_log (§6.1, supersedes decision #7):
  #   no match in the persistent allow-list -> held in `pending` for operator approval.
  # Sandbox-venue and rewritten-to-mirror fetches ride approved egress and are never held.
  unlisted_domain_policy: gate            # hard SSRF floor below is non-configurable regardless

fetch_rewrites: []                        # §6.1 — redirect/re-venue table (e.g. Maven Central -> Artifactory)

cache_dir: ~/.iceclimber-cache            # wheel/runtime cache, shared across sandboxes by platform fingerprint
approvals_file: ~/.iceclimber/approvals.json  # operator-owned persistent allow-list; never Nana-writable
```

`network.allowed_domains` is a **routing table**, not an access grant — the actual network boundary is enforced outside this tool. It tells Popo (a) which venue to use for a fetch (§6) and (b) whether an endpoint is the package mirror.

A hard-coded floor — blocking link-local/metadata-style addresses (e.g. `169.254.169.254`) and other obvious SSRF/lateral-movement targets — sits underneath `unlisted_domain_policy` and is **not** a config toggle. "Allow and log" governs arbitrary public domains, not the cloud's own metadata service.

## 4. Protocol — envelope and schemas

### Envelope

```jsonc
// outbox/new/<ulid>.json (request)
{
  "schema_version": 1,
  "id": "01J9XQK...",
  "type": "pip.install",
  "created_at": "2026-06-21T18:32:00Z",
  "params": { /* type-specific */ }
}
```

```jsonc
// inbox/new/<ulid>.json (response, same id)
{
  "schema_version": 1,
  "id": "01J9XQK...",
  "status": "ok",                 // ok | error | needs_clarification
  "completed_at": "2026-06-21T18:32:04Z",
  "result": { /* present if status=ok */ },
  "error": { "code": "...", "message": "...", "retryable": false },
  "clarification": { "question": "..." }
}
```

`status` describes whether Popo *successfully serviced the request*, not whether every sub-item inside it succeeded — e.g. a `pip.install` batch where 2 of 5 packages fail is still `status: ok`, with per-package failures inside `result`. `status: error` is reserved for Popo failing to even attempt it (malformed request, missing target runtime, internal exception).

**No `pending` stub is written.** (Decided: heartbeat-only liveness, see §4.7 — simpler, revisit only if it proves confusing in practice.) Absence of a response file means "still in progress." Nana polls with backoff and separately watches heartbeat staleness.

**Delivery semantics — at-least-once, deduped to effectively-once (v1).** The transport can drop or double-deliver, so:

- **Crash recovery.** The `new → cur` rename is the pickup-lock, but a request sitting in `cur/` when Popo dies (picked up, no response written) is orphaned. `serve` sweeps `cur/` on startup: any entry without a matching response in `inbox/` is re-processed (or written a `status: error` if non-idempotent — see below).
- **Dedup by `id`.** If an inbox response is lost and Nana re-submits the same logical request, Popo dedups on the envelope `id`: a request whose `id` already has a durable response replays that response instead of re-executing. `python.install`/`pip.install` are naturally idempotent; **`web.fetch` with a non-GET method is not** — for those, re-execution on an unconfirmed delivery is unsafe, so a recovered-from-`cur/` non-idempotent request is answered `status: error, code: interrupted_unsafe_retry` rather than silently re-POSTing.
- Responses are written durably (tmp-write + atomic rename, §6) so a half-written response never looks complete.

### 4.1 `ping`
```jsonc
params: {}
result: { "pong_at": "...", "popo_version": "0.1.0" }
```

### 4.2 `python.install` — *implemented (phase 3)*
```jsonc
params: { "version": "3.12" }   // minor version; Popo pins the exact patch
result: { "version": "3.12.13", "path": "/abs/.../bin/python3", "already_installed": false }
```
Popo resolves the exact patch from PBS's `latest-release.json` (tag + `asset_url_prefix`) and the release `SHA256SUMS` — picks the highest-patch `install_only` asset for the sandbox's `<arch>-unknown-linux-<gnu|musl>` triple, verifies its SHA256, and records the pinned version. The tree is extracted with the Go stdlib (no remote `tar`) and pushed over `RemoteFS` (either transport); `bin/python3` is then run over the exec channel to prove it executes (§2 boundary). Verified on Alpine/musl.

### 4.3 `pip.install` (batched) — *Tier 0 implemented (phase 4)*
```jsonc
params: {
  "python_version": "3.12",
  "packages": [{ "name": "requests", "version": "2.32.3" },  // pinned
               { "name": "rich" }]                            // unversioned -> native default
}
result: {
  "installed": [{ "name": "requests", "version": "2.32.3", "tier": "mirror", "sha256": "..." }],
  "failed": [{ "name": "foo", "version": "1.0", "error": "..." }]
}
```
`tier` ∈ `mirror | relay | built | subagent` — the audit trail (§5). **Resolve → retrieve (decision #21):** Popo first co-resolves the whole request against the index (`pip install --dry-run --report`) — native fidelity, exactly as installing a repo's requirements; an unsatisfiable graph fails the request (`resolution_failed`). It then installs each resolved package independently (`--no-deps`) so individual pull failures are per-package. **Versions need not be pinned in the *request*** (unversioned resolves by the manager's default) — but the *resolution* is always recorded with exact versions + sha256, so determinism lives at the resolved layer. (Supersedes the old "always pinned request" stance.)

### 4.4 `web.fetch`
```jsonc
params: { "url": "https://...", "method": "GET", "headers": {}, "body": null }
result: {
  "status_code": 200, "headers": {},
  "venue": "sandbox-exec",          // or "controller" — which side actually made the call
  "encoding": "utf8",
  "body_inline": "...",             // present if under ~16KB
  "body_blob": "blobs/<sha256>"     // present otherwise
}
```
See §6 for venue selection logic. **Phase 6a (implemented):** the **sandbox-exec
venue** — Popo runs curl, or busybox `wget`, *inside* the sandbox over the exec
channel (no Python; web.fetch is language-agnostic). Body returns inline
(utf8/base64) under 16 KB, else as `blobs/<sha256>`. The **controller venue** and
its policy layer (SSRF DNS floor, egress gating, fetch rewrites, pending/approve/
deny) are **phase 6b**.

### 4.5 `web.research` (sub-agent path) — `v2:` parked (§0)

> **v2.** Not in the first build — the thing in the sandbox is already a Claude agent, so a second research agent inside Popo is a separate product. v1 surfaces resolution ambiguity to the operator instead. Schema kept so v2 doesn't re-derive it.
```jsonc
params: { "question": "...", "context": "...", "max_iterations": 5 }
result: { "answer": "...", "sources": [{ "url": "...", "note": "..." }], "iterations_used": 3 }
```
**OPEN** — concrete tool loop, stopping criteria, prompt construction. See §10.

### 4.6 `capabilities.json` (self-reported by Nana once, not a queued request) — *superseded by decision #72*

> **Superseded (Phase 4, #72):** the schema below (`{has_exec, has_file_write}`,
> Nana-written) shipped only as a placeholder no production code wrote. It is now a
> CONTROLLER-written self-report — host facts (bootstrap) + the installed agent's
> identity (install/wrap) — and Nana writes nothing. The original §4.6 design is kept
> below for history.

```jsonc
// v1 shape — trimmed to fields something actually consumes (decision #14):
{ "has_exec": true, "has_file_write": true }
```
`has_exec` is the **viability gate**: only Nana knows whether its harness exposes an execution primitive that resolves paths against the tree Popo populates (§2 scoping boundary) — Popo's own SSH exec can't answer that. `has_file_write` is required to participate in the protocol at all. Dropped from v1: `has_network_tools` (Popo drives all fetches, §6) and `shell_hint` (ExecFS is pinned to POSIX sh, §6 — nothing branches on it). Re-add only when a consumer appears. *Phase 7: `NANA.md` instructs Nana to write this as its first action, and `status` **reads it where present** — Popo never requires it.*

### 4.7 Liveness — heartbeat by content, not mtime

Popo writes the heartbeat file's **content** (not mtime). This avoids needing any `stat`-equivalent on Nana's side (a portability trap under `ExecFS`, see §6) and works regardless of what Nana's harness tools expose — "read this file" is the only primitive required.

**Content is `<seq> <iso8601>` — a monotonic counter first, timestamp second.** Nana judges liveness primarily on **counter advancement** ("has `seq` increased across my last K polls"), which needs *no* clock synchronization between the two sides. Agent harnesses frequently have skewed or unreliable clocks, so comparing Popo's absolute timestamp against Nana's wall clock would produce false "Popo is down" verdicts. The timestamp is kept for human logs only, not for the liveness decision.

Skill-documented polling schedule: 2s / 5s / 10s / 30s backoff; if `seq` has not advanced across ~the last several polls (≈2 minutes of wall time at the tail of the backoff), stop waiting and surface "Popo appears to be down" rather than polling forever.

## 5. Package resolution tiers

Ordered by how much machinery each needs — always try the cheapest first:

- **Tier 0 — internal mirror, direct remote-exec.** *Implemented (phase 4).* Primary path. Popo remote-execs pip *inside* the sandbox against the mirror, using the sandbox's own already-approved egress — resolve (`--dry-run --report`) then per-package `--no-deps` install. No wheel transfer, no relay. Popo's commands pass `--index-url` **explicitly** (robust under non-interactive exec, decision #23); `bootstrap` *also* writes `state/pip.conf` so the agent's ad-hoc pip hits the same mirror. *(Tested against real PyPI as a stand-in mirror; the egress restriction itself is not yet modeled.)*
- **Tier 1 — Popo-side fetch + relay.** *Implemented (phase 5).* For packages the sandbox can't reach. Popo runs the **operator's `python3`** to `pip download --only-binary=:all: --platform <musllinux/manylinux tag(s)> --abi cp<ver> --python-version <ver>` (cross-platform, targeting the probed fingerprint), relays the wheels in via `RemoteFS` to `blobs/wheels-<id>/`, then remote-execs `pip install --no-index --find-links=… --report` in the sandbox (tier=relay, sha256 hashed from the wheels). The foreign-tag risk was **spiked and resolved** (musl-aarch64 wheels download cleanly from macOS, incl. C-extensions). Selected via `--tier relay` or `auto` when no mirror is set (decision #24–25). Sdist-only packages have no wheel ⇒ Tier 2 build (parked v2).
- **Tier 2 — build-on-controller fallback.** `v2:` parked (§0). Compiled extension, no matching wheel anywhere. Popo builds it in a container/VM matching the probed fingerprint, then drops into Tier 1's transfer mechanics. **OPEN** — exact container strategy. *v1 behavior: fail loudly ("no wheel anywhere; add it to your mirror"), don't build.*
- **Tier 3 — sub-agent.** `v2:` parked (§0) — see §4.5. Genuinely ambiguous resolution, or recovery from a Tier 0–2 failure.

Python itself is always relay-based (Tier 1-style transfer) — nothing exists in the sandbox yet that could pull it from anywhere, mirror or not. *Implemented in phase 3.* **Shebang note (decision #20):** PBS's `bin/python3` is relocatable and runs by absolute path with no shebang reliance, so phase 3 needs no rewriting. `pip`-installed console scripts *do* bake an absolute shebang at the install path — that bites in **phase 4** (pip), where entry points get shebang rewriting or `python3 -m` invocation. Deferred there, not here.

**Determinism note:** regardless of tier, the resolved package hash is always recorded in the response (§4.3) — "company-approved" doesn't mean unverified.

## 6. Network — fetch venues and transport

### Two fetch venues

Because Popo sits *outside* the corporate network and the sandbox sits *inside* it, fetches need two execution venues, chosen automatically per target rather than guessed:

- **Controller-side**: Popo fetches from its own network. Right for general internet / public resources.
- **Sandbox-side (remote-exec)**: Popo uses its existing SSH exec access to issue the fetch *from inside the sandbox's network position*, then relays the result back through the inbox file. Required for anything only reachable from where the sandbox sits (the internal mirror, internal docs, etc.) — and Popo can do this without Nana's own harness having any network tool, since Popo is driving the SSH exec channel directly.

Sandbox-side fetches use **curl when present, else busybox `wget`** (which does HTTPS, `--header`, `-O`, and `-S` for the status line) — **not** Python (decision #28; web.fetch must not be tied to the Python runtime). A box with neither curl nor wget is reported clearly.

### 6.1 Egress gating & fetch rewrites (v1) — *implemented (phase 6b)*

*Realized in `internal/egress` (policy + rule/pending stores) + `internal/webfetch` (controller venue, SSRF-safe dial) + the `pending`/`approve`/`deny` CLI. Plain `approve <id>` grants host scope (`--remember` for a custom glob); unlisted URLs default to controller-gated; `deny` persists a deny rule; the SSRF floor blocks private/link-local/metadata at dial (rebinding-resistant) and refuses literal blocked IPs up front.*

`web.fetch` via the **controller venue** is a deliberate tunnel through the sandbox's egress isolation: it lets an in-sandbox agent reach the public internet — including arbitrary POST bodies — from Popo's network position. That is the *point* (the sandbox can't egress on its own), but it is also a data-exfiltration path that defeats the sandbox's reason to exist, so it is **gated, not free**. The SSRF floor alone (blocking `169.254.169.254` and friends) does not address this — "the agent can `POST` whatever it scraped to an arbitrary public host" is the larger threat, and it is what the gate is for.

Two mechanisms run **in order**, before any controller-venue fetch:

**1. Rewrite table — redirect/re-venue before gating.** Generalizes pip.conf's `index-url`: a naive public URL is mapped onto the internal mirror that actually serves it, and re-tagged to the venue that can reach it. A request that rewrites onto a sandbox-reachable mirror **needs no approval** — it never leaves the approved network.

```yaml
# iceclimber.yaml
fetch_rewrites:
  - match: "https://repo1.maven.org/maven2/*"
    rewrite_to: "https://artifactory.corp.internal/maven-central/*"
    venue: sandbox            # rewritten target rides the sandbox's already-approved egress
  - match: "https://pypi.org/*"
    rewrite_to: "https://artifactory.corp.internal/pypi/*"
    venue: sandbox
```

Rewrites are operator-owned config (never Nana-writable). Matching is prefix/glob; the trailing `*` captures the path tail and is appended to `rewrite_to`. The audit entry records both the original and rewritten URL so the redirect is never silent.

**2. Approval gate — for fetches that survive rewriting and still aim at the public internet.** Checked against the operator's **persistent allow-list**:

- **match → allow**, audited.
- **no match → held**: the response is `status: needs_clarification`; the request lands in `pending`; Nana polls/backs off (§4.7). The operator then runs:
  - `approve <id>` — one-shot, this request only.
  - `approve <id> --remember <pattern>` — **persists** an allow rule (e.g. `https://docs.python.org/*`); all future matching controller-venue fetches auto-allow. This is the "permanent approval on Popo's side."
  - `deny <id> --reason "..."` — Nana gets `status: error`, `code: egress_denied`.

The allow-list and rewrite table live in **operator-owned state**, never writable by Nana. Sandbox-venue fetches and rewritten-to-mirror fetches are **never held** — they ride approved egress.

This is the concrete trigger §10 flagged as missing: **approval gates controller-venue egress, not "unlisted domains."** It supersedes the old `allow_and_log` default for the controller venue (decision #7).

**Per-verb kill switch (coarse control).** `serve --deny web.fetch` disables the verb entirely. The verb allowlist Popo serves *is* the security boundary: any file in `outbox/new` is treated as fully operator-authorized (file presence is the only authentication — acceptable for a single-operator laptop tool, stated explicitly so it isn't assumed otherwise). The SSRF floor sits underneath everything and no rewrite or allow rule can reach a link-local/metadata target.

### Transport abstraction: `RemoteFS` — *implemented (phase 2)*

```go
// internal/remotefs — all paths absolute; missing path -> errors.Is(fs.ErrNotExist)
type FS interface {
    Mkdir(ctx, path string) error            // mkdir -p / MkdirAll
    WriteFile(ctx, path string, data []byte) error
    ReadFile(ctx, path string) ([]byte, error)
    List(ctx, dir string) ([]string, error)   // sorted basenames; empty dir -> ([],nil)
    Rename(ctx, old, new string) error          // POSIX replace semantics
}
```

*Refined from the original `WriteAtomic(dir,filename,io.Reader)` sketch (decision #16):* the FS exposes primitive `WriteFile` + `Rename`, and the **maildir layer composes atomic delivery** (write to `tmp/`, rename into `new/`) so readers of `new/` never see a partial file. `data` is `[]byte` for now; a streaming `io.Reader` variant arrives with blobs (phase 3+).

Two implementations, chosen at session open based on whether the SFTP subsystem is actually available (it's sometimes disabled even when exec works); `--transport auto|sftp|exec` overrides (the override exists so the functional suite can exercise ExecFS even where SFTP works):

- **`SFTPFS`** — the fast path (`pkg/sftp`; `PosixRename` for atomic replace).
- **`ExecFS`** — built from day one (decided in review, not deferred), for sandboxes with the SFTP subsystem disabled.

A single conformance suite (`remotefstest.RunConformance`) runs against both — locally (host shell + in-process `net.Pipe` SFTP) **and** against the real Alpine VM over both SSH channels — asserting identical behavior (write/read roundtrip incl. NUL bytes, empty-directory handling, missing-path `ErrNotExist`, rename replace+source-gone). Nothing above this layer (probe, bootstrap, the dispatcher) ever knows which implementation is active.

**`ExecFS` command palette (pinned, not allowed to grow ad hoc):** `sh`, `mkdir -p`, `cat`, `mv`, `rm -f`/`rm -rf`, `ls -1`, `wc -c`, `chmod` (octal), `ln -s`, shell redirection, `&&`. No GNU-specific flags, no `stat` (flags differ across GNU/BSD/busybox). `chmod`/`ln -s` were added in phase 3 for the executable bit + symlinks a relocatable interpreter needs (decision #19); `RemoveAll` (`rm -rf`) added in phase 5 (decision #27). A sandbox lacking even this set is out of scope — stated explicitly rather than discovered later.

**Raw streaming over base64.** A non-pty exec channel is a clean byte stream — `cat > path` with content piped directly into the channel's stdin avoids ~33% base64 overhead. Never request a pty (ptys are what mangle bytes). Base64 kept in reserve only as a defensive fallback if some sandbox proves to mangle raw streams.

**Bulk transfer under `ExecFS`.** ✅ **Done (decision #55).** Naively opening one SSH channel per file (a runtime distribution is thousands of files) is slow — each channel open is its own round trip. The original sketch was a custom length-prefixed wire protocol; the shipped solution is simpler and needs no new protocol: a runtime push goes through `remotefs.PushTarGz`, and any `FS` that implements the `TreePusher` capability (`ExecFS` does) receives the whole tree as **one** `tar -xf - -C <target>` exec, the tar streamed into stdin. Gunzip and strip-leading-component are done controller-side in Go (re-taring on the fly) so the sandbox `tar` needs no `-z`/`--strip-components` — BusyBox `tar` suffices and preserves mode bits + symlinks. A plain `FS` (no `TreePusher`) still falls back to per-file `WriteFile`/`Chmod`/`Symlink`. This removed the v1 "**requires `SFTPFS` for `python.install`**" constraint — every language installs over either transport now, verified by `TestPythonInstallOverExec` on the BusyBox sandbox.

**Extraction trick (both transports).** Extract the Python distribution archive **on the controller** (which definitely has tar/zstd) and push the already-extracted directory tree file-by-file, rather than requiring the sandbox to have `tar`/`zstd`/`unxz` itself. A remote-tar fast path can be added later purely as a speed optimization once it's known to matter, never as a requirement.

### Security floor (not configurable)

- Hard block on link-local/metadata-range addresses and obvious internal-pivot targets, regardless of `unlisted_domain_policy`.
- Every `web.fetch`/`web.research` call gets an append-only audit entry: URL, venue, status/size, timestamp. Bodies are hashed rather than stored in full. *Resolved (phase 6a, decision #30):* **controller-side** JSONL (Popo's copy is authoritative, §3), one file per `sandbox_id`, schema `{ts, id, type, url, method, venue, status_code, body_size, body_sha256, outcome}`. Retention is unbounded for now (append-only); rotation is future work.

## 7. Bootstrap & probe sequence

1. **Connect & verify channels.** SSH connect, then verify `exec` and `sftp` independently — don't assume one implies the other. If `exec` fails, bootstrap fails immediately; if `sftp` fails, fall back to `ExecFS` (§6).
2. **Fingerprint the sandbox.** OS, arch, libc (multiple independent signals — disagreement ⇒ low confidence), free disk space, an actual write test (not just permission bits) at each install-root candidate, detection of an existing iceclimber tree (idempotent re-bootstrap). Every probe command is plain POSIX `sh` — no bashisms. Low-confidence fields pause bootstrap and ask the operator to confirm rather than guessing.
3. **Choose the install root.** First writable, durable candidate wins (operator-supplied path checked first, then `$HOME/.iceclimber`, then `/opt/iceclimber` as a root-only long shot). **Decided:** if none is writable, bootstrap fails and requires an explicit operator-supplied path — `/tmp` is never used as a silent fallback, since installs that vanish on reboot defeat the point.
4. **Create the tree & drop the skill.** Maildirs, `blobs/`, `runtimes/`, `state/`, `pip.conf` (safe to write before Python exists). `NANA.md` is written into the tree regardless of harness; the operator gets a printed reminder that wiring it into their specific harness's instructions is a manual integration step Popo can't auto-detect.
5. **Smoke test, no agent involved.** Popo writes a synthetic `ping` directly into `outbox/new` itself, runs one dispatch cycle, confirms `pong` lands in `inbox/new`. Isolates "is the plumbing broken" from "is the agent using it correctly."
6. **Report to operator.** Fingerprint, chosen root, channel capabilities, smoke-test result, skill path, any low-confidence flags. Refuses to proceed to `serve` if critical capabilities (exec) are missing.

`probe` (read-only, phases 1-3 minus writes) is a separate command from `bootstrap` (full idempotent setup) — useful as a standalone diagnostic ("is the box still reachable, has disk filled up") without touching anything.

## 8. Fleet extensibility — `v2:` parked (§0)

> **v2.** "Design for it now, build for one" is exactly the unrequested-flexibility the general principles warn against. v1 keeps **only** the `sandbox_id` namespacing below (cheap, one directory level) and the cache-by-fingerprint key; it does **not** build worker-pool or multiplexing machinery. v1's fleet story is literally "run N independent `serve --sandbox X` processes," which needs no fleet design — just no global singletons. The rest is preserved here for when a second sandbox actually arrives.

- All of Popo's local state (probe results, request/response logs, in-flight tracking) is namespaced by `sandbox_id`, even with only one configured today.
- The package/wheel **cache** is namespaced differently — by platform fingerprint (arch/libc/python version), not sandbox — since that's what's actually shareable across a future fleet.
- The `serve` loop is one worker per SSH connection, so "N sandboxes" later is "spawn N workers," not a rewrite.
- v1 fleet story: run N independent `iceclimber serve --sandbox X` processes side by side. A true multiplexed daemon is optional future work, not required now.

> **Status update (2026-07):** the "second sandbox" has arrived on the roadmap. The full
> fleet design — agreed with the operator, **not yet built** — is **§14**; the prerequisites
> (per-sandbox locks #88, the `--sandbox` selector + reserved `all` namespace #89, the shared
> artifact cache #90, the `sandboxWorker`/tagging/approvals-queue #91) are all shipped.

### Testing strategy

Tiers, run at different frequencies (washu testing guide):

- **Unit** — fast, every change. Mock at the `remote.Runner` boundary; table-driven parsers/detection logic (`internal/probe`, `internal/config`). Run with `go test -race ./...`.
- **TUI flows** — fast, no VM, but driven through the **real Bubble Tea runtime** via `teatest` (`internal/tui/flows_test.go`): keys and messages go through the genuine event loop and huh form, asserting on rendered output + the operator actions that fire. This is the interactive analogue of the CLI's stdin/stdout tests. **Rule: every TUI flow — every key, modal, form field, and state transition — has a flow test**, so the console is confirmed end to end, not approximated. (huh advances fields via async cmd round-trips, so checkpoint each field's placeholder before typing.)
- **Functional (E2E)** — low-frequency, real dependencies. Black-box: the **real binary** drives a **Lima/Alpine** sandbox over SSH (`test/functional/`, `//go:build functional`, `make e2e`). The console's operator-action executor has its own white-box functional test (`make tui-functional`: install + bootstrap against the VM, asserting Nana's echo). Alpine = **musl + BusyBox** is deliberate — it enforces the "POSIX sh only, no GNU-only flags" discipline (§6, §7) and exercises musl libc detection. Each phase adds its functional test here (phase 2: maildir `ping`/`pong`; etc.), so "test as we build" holds. These run with **open internet** — they prove the mechanism, not the air-gap premise.
- **Acceptance (opt-in)** — the whole premise, end to end: a real Claude agent in an **air-gapped** sandbox (`test/demo/`, `//go:build demo`, `make demo`). Needs a Claude **subscription** token (`DEMO.md`); never part of `make test`. This is the only tier that simulates the no-egress boundary the design exists for.

## 13. Prior art — A2A (Agent2Agent), considered & not adopted

A2A (Google, now v1.0 / Linux Foundation, ~150 orgs as of 2026) is an open protocol for **independent, network-reachable agents to discover and delegate to each other**: JSON-RPC 2.0 over **HTTPS**, SSE streaming, push notifications, discovery via a signed **Agent Card** at a well-known HTTP endpoint.

**Not adopted for the Popo ↔ Nana link — transport mismatch with the project's defining constraint.** Every A2A assumption (an HTTP server, a reachable endpoint, a served Agent Card) is precisely what the architecture refuses to require: an **SSH-only** link, a sandbox with **no assumed network listener and no egress**, and a Nana whose only guaranteed primitive is **file read/write** (§2, §4.6). Adopting A2A would re-introduce the exact assumption the maildir-over-SSH design exists to avoid. This is a firm rejection, not a "maybe later."

**Borrowed concepts (no dependency taken):**
- **Agent Card → `capabilities.json` (§4.6).** Same capability-self-description instinct; loosely align vocabulary. Reinforces pruning `capabilities.json` to fields something actually consumes.
- **Task state `input-required` → `needs_clarification`.** Borrow the *naming* for legibility; do **not** adopt A2A's full task state machine (decision #8's "no pending stub, heartbeat-only" is simpler and stays).

**Possible v2 re-entry, controller-side only:** if the v2 `web.research` sub-agent (§4.5) ever delegates to external specialist agents, **Popo** (which has real internet) could act as an A2A *client* — outbound HTTP from the controller, never touching the sandbox link. Noted, not designed.

## 14. Phase 3 — the multi-sandbox fleet (DESIGNED 2026-07, not yet built)

Designed with the operator across two decision rounds; every choice below marked
**[decided]** is settled — the rest is engineering judgment recorded here so
implementation doesn't relitigate it. Prerequisites all shipped: per-sandbox two-tier
locks (#88), the `--sandbox` selector with the reserved `all`/glob namespace (#89), the
fingerprint-keyed shared artifact cache with per-asset flock (#90), and the
`sandboxWorker` + `tui.SandboxMsg` tagging + approvals queue (#91).

### 14.0 Goals / non-goals

**Goal:** one operator supervising **2–10 sandboxes, attended** [decided] from one
console and one CLI, with fleet-wide provisioning that downloads once and pushes N
times. **Non-goals (deferred until a real fleet demands them):** 50+ unattended scale
(idle-backoff pollers, rules-first approval batching, metrics export), multi-controller
coordination (two operator machines sharing a fleet), and any sandbox-side change — the
agent, `popo`, NANA.md, and the maildir protocol are **fleet-invariant**; a sandbox never
knows it has siblings.

### 14.1 Config — one file, `defaults:` + `sandboxes:` map [decided]

```yaml
# iceclimber.yaml — a fleet
defaults:                      # a Config template every member inherits
  ssh: { user: agent, keepalive_interval: 20 }
  egress_mode: relay
  dispatch_concurrency: 4

sandboxes:
  ci-1:    { ssh: { host: 10.0.0.5 } }
  ci-2:    { ssh: { host: 10.0.0.6 } }
  gpu-box: { ssh: { host: gpu.corp }, egress_mode: proxy }
```

- A classic single-sandbox file (`sandbox_id:` + `ssh:` at top level) stays valid
  unchanged — it *is* a one-entry fleet. The two shapes are mutually exclusive in one
  file (`sandbox_id` + `sandboxes` together = validation error).
- **Merge rule:** each member = `defaults` deep-merged with its entry, entry winning
  field-wise; nested structs merge per field, scalars/lists replace. *Mechanism
  (resolved at design time):* decode `defaults` into a `Config`, then decode the
  member's `yaml.Node` **onto the same struct** — yaml.v3 only assigns keys present in
  the document, so presence-vs-zero is exact (`password_auth: false` in an entry
  correctly overrides a `true` default; an absent key inherits) with no pointer fields
  and no custom merge code. Test both override directions for booleans/ints anyway.
- Fleet membership is the map, **only** — the per-file `--sandbox` search conventions
  (#89) keep working for addressing a *single* box but do not add members (one
  membership mechanism; no union/dedup rules to explain).
- `config validate` validates every member post-merge and reports per-member errors.

### 14.2 Targeting — `--sandbox` selectors [decided]

`all`, globs (`ci-*`), and comma-lists (`ci-1,stage`) resolve against the map (the #89
reservation becomes real). Defaults with a fleet config present:

| Command class | No `--sandbox` given |
|---|---|
| `iceclimber` (console), `serve` | **all** — that's why a fleet file exists |
| Read-only: `status`, `logs`, `egress pending` | **all** |
| Mutating one-shots: `install *`, `bootstrap`, `agent install` | **error** naming the members + `--sandbox all` — a forgotten flag must never fan a mutation to N boxes |
| Inherently single-box: `shell`, `setup`, `trust`, `web fetch`, `maven build`, `skill path` | **error** asking for one box; `all`/globs rejected with a clear message |

### 14.3 The fleet console — overview + per-sandbox tabs [decided]

- **Tab 0 — overview:** one row per member: link state (`● serving` / `◌ reconnecting` /
  `⛔ owned by pid N (role)` / `✗ unreachable`), heartbeat seq/age, serviced count,
  **pending-approvals badge**, last action. The row set is the fleet's health at a glance.
- **Tabs 1–9:** exactly today's single-sandbox console per box (panes, meters, panels,
  forms — `tui.Console` unchanged as the per-sandbox view, per #91's explicit decision).
  Keys: `0` overview, `1`–`9` direct, `[`/`]` cycle, `esc` = back to overview from a tab
  (consistent with esc-as-back, #88). The footer shows the active sandbox name.
- **Approvals are global:** any member's approver feeds the ONE modal queue (#91),
  labeled with its sandbox (the `ApprovalRequest.Sandbox` field + `SandboxMsg` tag);
  answering never requires switching tabs. Tab badges + an overview column show queued
  counts. Password prompts likewise (already queued).
- **Startup:** N workers start concurrently. A member whose initial dial fails does NOT
  abort the fleet — it renders as `✗ unreachable`, retried on the reconnect cadence.
  *Engineering note:* today's `startSandboxWorker` is dial-then-error; the fleet shell
  wraps it in an async start with a connecting/failed row state (the single-box path
  keeps fail-fast). First-contact trust prompts (untrusted host keys) run sequentially
  BEFORE the alt-screen, one per untrusted member, each skippable (skip = that member
  starts unreachable).
- **Architecture:** a `fleet` tea.Model owns `map[id]tui.Console` + the overview,
  routing every `SandboxMsg` by ID to its member view; untagged messages route to the
  active tab (N=1 compatibility). One events channel, N workers fanned in.

### 14.4 Locks — partial acquisition [decided]

The fleet console/serve acquires each member's `serve.lock` independently: **serve what's
free, show what's not** (`⛔ owned by pid · role` rows), and retry-acquire periodically so
a member joins live the moment its other owner exits. Headless `serve --sandbox all`
mirrors this (warning per conflicted box; non-zero exit only if NOTHING was acquired).
Rationale: during an incident, a partial fleet beats no fleet; the ⛔ row keeps ownership
visible instead of silent.

### 14.5 Fan-out — parallel, keep going, summarize [decided]

`install */bootstrap/agent install --sandbox all|glob|list`:

- All targets run **concurrently** (bounded: min(N, 4) simultaneous dials — SSH auth
  prompts serialize via the caching prompter; the artifact cache's per-asset flock (#90)
  makes the same download happen once no matter how many boxes want it).
- Output prefixed `[box]` line-wise; a member's failure never aborts the others.
- Ends with a summary table (`ok: …` / `failed: box (reason)`), exit 1 if any failed.
- **Version consistency:** the requested version is resolved **once** (first resolve
  wins) and the exact resolved version (e.g. 3.12.13) is installed on every member —
  N boxes must not end up on different patch releases because an index updated
  mid-fan-out. Heterogeneous fleets (mixed arch/libc) resolve per-platform *assets* for
  that one version; a platform with no asset for it fails that member, not the fleet.
- Per-member ops locks apply as today (the fan-out takes each member's `ops.lock`).

### 14.6 Fleet-aware surface, first release [decided]

`console/serve · status (table) · logs (merged, [box]-tagged) · install python|pip|node|
npm|java|maven|conda|shell · bootstrap · agent install · egress pending (merged)` — and
`egress approve|deny <id>` search every member's pending store (ULIDs don't collide).
Everything else stays single-box with a clear error. `setup` remains single-box by
design: first contact (trust fingerprints, tokens) deserves per-box attention.

### 14.7 Failure modes (design-level answers)

- **A member down mid-serve:** its worker reconnects forever (existing supervisor);
  overview shows `◌`; nothing else is affected.
- **Fleet console quits:** all workers stop; every member's pending approvals fail safe
  to deny (existing done-close semantics), locks release via flock-on-exit.
- **Two fleet consoles, overlapping subsets:** each serves what it can lock; both
  overviews show the other's members as ⛔ — no double service possible (#88).
- **Config edit while serving:** not hot-reloaded in v1; restart the console (note in
  docs; hot member add/remove is a deferred nicety).

### 14.8 Implementation sketch (for when we build — NOT now)

1. `config`: `defaults`/`sandboxes` schema + merge + validation + `Members()`;
   selector resolution (`all`/glob/list → []Config). Unit-heavy.
2. CLI targeting: the per-class default/require/reject matrix (14.2) in one helper;
   fan-out engine (14.5) with summary rendering; wire the fleet-aware commands.
3. Fleet console: async worker start, the `fleet` model (overview + routing +
   tab chrome), lock-retry rows, trust-prompt sequencing. teatest flows per key/state.
4. Functional: two-member fleet against the two existing VMs (musl + glibc boxes make a
   genuinely heterogeneous fleet!) — fleet status table, fan-out install (resolve-once
   asserted via both boxes reporting the same version), lock-overlap rows, merged logs.
5. Docs (README fleet section, QUICKSTART "growing to a fleet"), decision entry.

Estimated as 3 batches (config+CLI · console · functional/docs), each gate-able alone.

### 14.9 Deliberately deferred

Idle-backoff pollers + approval batching (needed ~N>20), a fleet daemon/API, hot config
reload, multi-controller fleet sharing, per-member colour theming, `setup --sandbox all`.
Each waits for a demonstrated need (§0 discipline).

### 15.1 One gated intake, three producers [decided]

tasks.yaml — pre-trusted, straight to the queue), a **sandbox agent**
(`popo task.propose` — held in proposals/), and the future **controller-side planner**
(§15.6 — also writes proposals/). `task approve|deny` moves a proposal into tasks.yaml
or drops it — machine-authored tasks never enter the queue unreviewed, regardless of
author. Task schema: `id`, `prompt`, optional `after: [ids]` (dependencies — Popo only
hands out tasks whose deps are done [decided]), optional `sandbox:` pin, optional
`timeout:`. Intent (tasks.yaml) and state (ledger/state.json) are deliberately separate
files with separate owners.

### 15.2 The verbs (the maildir is the task bus) [decided]

- **`task.next {goal?}`** → `{task_id, prompt, goal, inputs: [<root>/shared/in/<dep>/…]}`
  or "none". Popo picks the first eligible task (deps done, unleased, pin matches),
  records the lease (sandbox, ts) in the ledger, and **pushes the `after:` dependencies'
  artifacts into the sandbox first** so the assignment arrives with its inputs.
- **`task.report {task_id, status: done|failed|blocked, summary, attach: [paths]}`** —
  Popo pulls attachments into `artifacts/<task-id>/` (per-attach size cap, config),
  appends the ledger, releases the lease. `blocked` carries a question (the
  `needs_clarification` pattern): the task leaves the queue until the operator answers
  (`task answer <id> "…"` — the answer is appended to the task's prompt and it becomes
  eligible again).
- **`task.propose {prompt, after?, reason}`** → a proposals/ file; ack returns the id.
- **Atomicity across processes:** assignment mutates shared state, and N sandboxes may
  be served by N processes — `task.next` takes a flock on the goal store (the
  logfile/relay pattern). This makes shared goals work WITHOUT the fleet console: N
  independent serves coordinate through the store, so §15 does not depend on §14's
  build order.
- PROTOCOL.md gains the three verbs; NANA.md gains a "Working shared tasks" section
  (mode-independent — task verbs are egress-agnostic).

### 15.3 The worker loop — fresh agent per task [decided]

A dropped `<root>/worker` script (the launcher pattern, #58/#87):
`while task=$(popo task.next); do nana -p "<task prompt>"; done`. The AGENT calls
`task.report` itself (NANA.md contract — it knows the outcome); if the nana process
exits without reporting, the worker reports `failed` on its behalf (crash containment,
mirroring the #185 capping-tee philosophy: the harness guarantees the invariant the
agent might miss). Fresh context per task — no drift/bloat; reports + artifacts carry
the baton between tasks. One lease per sandbox at a time.

### 15.4 Leases — TTL → stale → operator requeues [decided]

Default 30m TTL (per-task `timeout:` override). Past TTL the task shows **⚠ STALE**
(console + CLI, loudly) but reassignment is the OPERATOR'S call (`task requeue`) —
slow ≠ dead is a human judgment at attended scale, and auto-requeue risks two agents on
one side-effect-laden task. Conflict rule: a late report for a requeued task is recorded
in the ledger as `late-report` but does NOT change task state (the current lease's
report wins).

### 15.5 Artifacts — Popo-mediated hand-off [decided]

`task.report --attach` pulls controller-side; `task.next` pushes dependency artifacts
in. Transport-agnostic and strict-air-gap clean: works identically in relay and proxy
modes, requires NOTHING new in the sandbox. The named v2 upgrade for tight same-repo
collaboration: a controller-hosted bare git repo served over the egress proxy (rewrite
rule → local `git http-backend`), proxy-mode only, requires git in the sandbox —
designed as the upgrade path, deliberately not part of this feature's first build.

### 15.6 The planner — a Popo-side Nana, designed only [decided: strictly no build]

The operator's ideal decomposition flow: **a planning chat with an agent on Popo's
side**. `iceclimber plan [--goal g]` launches the OPERATOR'S OWN local agent (e.g.
their `claude` CLI — the controller is a trusted machine with real internet) with a
`PLAN.md` skill contract, mirroring the Nana pattern exactly: agent + embedded skill
doc + a narrow contract. Its context: the goal description, current tasks, ledger
summaries. Its ONLY output artifact: a **proposal file** (the same schema
`task.propose` produces). The operator chats the decomposition out in their terminal,
then `task approve`s the results — the planner is just the third producer into the one
gated intake, so machine-authored decomposition gets exactly the same review as a
sandbox agent's proposal. No new protocol, no new trust surface. Terminal-native chat
first; an in-console chat panel is a much later nicety.

### 15.7 Operator surfaces [decided]

CLI: `iceclimber task add|list|show|approve|deny|requeue|cancel|answer` with `--goal`
(default "default"; goals are a grouping flag, not a noun — one noun until real
multi-goal usage argues otherwise) and `--json` on list. Console: a `t` tasks panel
(list + approve/deny/requeue/answer keys — CLI parity) and a TASK column in the §14
fleet overview (what each sandbox is working on). `iceclimber plan` reserved for §15.6.

### 15.8 Implementation sketch (for whenever the operator says build)

1. Store + verbs + CLI: goal store (flock, ledger, state snapshot), task.next/report/
   propose handlers, the `task` command group. Unit-heavy (lease/deps/stale/conflict).
2. Worker loop + contracts: `<root>/worker`, NANA.md/PROTOCOL.md sections, console
   `t` panel + fleet TASK column.
3. Functional: a real two-sandbox shared goal on the existing musl+glibc VMs — a
   dependency chain where box A's artifact feeds box B's task, a stale-lease requeue,
   a gated proposal; docs + decision entry. (The planner is its own later increment.)

### 15.9 Deferred, named

The planner build (§15.6), the shared git remote (§15.5), auto-requeue/retries,
multiple workers per sandbox, goal lifecycle state, unattended operation, in-console
planner chat.

## 16. The tool catalog — data-driven utilities (BUILT 2026-07, decision #97)

Designed with the operator. Unlike §14/§15 this one is scheduled: it **shrinks existing
code** (the shell installer becomes its first data entry), agents gain requestable tools,
and fleet fan-out should be born provisioning from it — so it builds next, before §14.

### 16.0 Scope [decided]

**In:** utilities — static binaries and simple archives (bash, ripgrep, jq, …) —
described entirely by data; adding one is editing a YAML file, not writing Go.
**Out, named:** language-runtime resolvers stay in Go (three quirky upstreams don't
justify owning a selector DSL — "code in YAML" is the trap; the marginal cost of a new
language post-#90 is ~80 lines + wiring, and table-driven wiring is the honest fix);
runtime **pin overlays** (operator-pinned exact assets/mirror URLs bypassing live
resolvers — the compliance mode) and **agents-as-catalog-entries** are deferred
extensions the schema must not preclude; package ecosystems (pip/npm/maven/conda) are
irreducibly code and already data-parameterized where sane (indexes/registries).

### 16.1 Format: our schema, others' conventions [decided]

Prior art evaluated: **aqua-registry** (closest — declarative, 2000+ packages, but its
schema encodes aqua's runtime semantics, libc isn't first-class, and checksum policies
vary), Hermit (HCL + install stanzas, dev-machine philosophy), asdf/mise (plugins are
shell scripts executing on the target — violates the BusyBox/trust model), ubi
(checksum-optional heuristics), nix (a platform takeover + sandbox-side requirements).
Verdict: **adopt conventions, not a foreign format** — most static tools follow
"GitHub release + SHASUMS file", so a few Go resolver *kinds*, fully parameterized by
data, cover the long tail while the schema stays ours: fingerprint-first
({os, arch, libc} — load-bearing for us, an afterthought elsewhere) and
**checksum-recipe mandatory** (an entry with no way to verify content is rejected at
load — the pinning discipline is the product for the air-gapped audience). An
aqua-registry *importer* (mine their URL/checksum data into our schema, pinned at
import, operator-reviewed) is a named later addition, not a v1 dependency.

### 16.2 The schema (v1)

```yaml
# one entry; a catalog file holds a list
name: ripgrep
description: fast grep (agents love it)
kind: github-release            # static-pinned | github-release | shasums-index
repo: BurntSushi/ripgrep        # kind-specific
version: "14.1.1"               # v1 is PINNED-ONLY (embedded and operator entries
                                # alike): no floating "latest", no {version} templating,
                                # no GitHub API dependency — bumping a tool is editing
                                # this file. "latest" arrives with the importer (§16.7).
platforms:                      # explicit per-platform table — data over clever
  linux/aarch64/musl:           # templating; template sugar can come later
    asset: ripgrep-14.1.1-aarch64-unknown-linux-musl.tar.gz
  linux/x86_64/musl:  {asset: ripgrep-14.1.1-x86_64-unknown-linux-musl.tar.gz}
  linux/x86_64/glibc: {asset: ripgrep-14.1.1-x86_64-unknown-linux-musl.tar.gz}  # static: musl runs on both
checksums: {recipe: shasums-file, asset: ripgrep-14.1.1-checksums.txt}
            # or, for kind static-pinned: per-platform {sha256: …} inline
unpack: {format: tar.gz, strip: 1, bins: [rg]}   # or {format: binary, bins: [name]}
verify: "rg --version"
```

- `kind` strategies (Go, data-parameterized): **static-pinned** (URL + sha per platform
  — the bash-static pattern, zero network beyond the asset), **github-release** (asset
  + sums file fetched from the PINNED release tag), **shasums-index** (index URL +
  SHASUMS convention, for non-GitHub upstreams). All names are literal strings — no
  template variables in v1 (pinned-only makes them unnecessary).
- **Checksum-file grammar (v1):** the standard two-column `<sha256>  <filename>` format
  only; per-asset `.sha256` sidecar files are a later recipe variant (§16.7).
- All fetching/verifying/caching is `internal/relay` (#90) — the catalog is purely the
  data that parameterizes it. Cross-process cache safety, download-once/push-N, and the
  `cache list/prune` surface (#94) apply unchanged.

### 16.3 Catalog locations + trust [decided]

Embedded defaults (a small curated set shipped in the binary: bash — migrated from
internal/shell — plus a shortlist chosen at build time, e.g. ripgrep/jq; every embedded
entry version-pinned with pinned checksums) + an **operator overlay**:
`~/.iceclimber/catalog/*.yaml` and a config `catalog:` path list. Operator entries
override embedded ones by name. Catalog files are **operator-owned** (the
approvals.json trust class): agents can request installs from the catalog, never extend
it. `iceclimber catalog list` shows entries + their source (embedded/operator) +
installed state; `--json` included.

### 16.4 Sandbox layout + surfaces [decided]

- Tools install to `<root>/tools/<name>/…`, with each entry's `bins` **linked into
  `<root>/tools/bin/`** — one stable PATH entry (added to `shell.EnvPreamble` and the
  launcher env) instead of a per-tool glob. Idempotent via the relay Exists probe;
  verified via the entry's `verify` command.
- **bash migration:** the catalog entry pins `dest: shell/` so `<root>/shell/bash` stays
  exactly where `iceclimber shell` (#87) expects. The schema has **no post-install
  hooks** (hooks are code-in-data — the same trap as declarative resolvers): the
  `install shell` ALIAS does catalog-install THEN drops the rc in Go, where the rc/env
  rendering already lives (internal/shell keeps exactly that; its installer/resolve code
  is deleted). A bare `install tool bash` installs just the binary.
- **Upgrades:** reinstalling an entry whose version changed replaces `tools/<name>/`
  wholesale (an iceclimber-owned dir; old bin links removed, new ones made). Same
  version = the idempotent already-installed path.
- CLI: `iceclimber install tool <name>` (+ `catalog list`). Console: the install form's
  language select gains "Tool", with a picker over the catalog. Agent:
  **`popo tool.install <name>`** — a normal approval-gated verb ("Install tool ripgrep
  14.1.1" · y/a/n/d), dispatch-serialized per tool (`tool:<name>` family key), with an
  unknown name answered by the available list. Wire schema: `tool.install {name}` →
  `{name, version, path, already_installed}` (the PROTOCOL.md verb-table row). NANA.md
  gains two lines ("ask Popo for common Unix tools by name").

### 16.5 Validation + failure modes

Catalog load validates every entry (schema, platform keys against the known fingerprint
vocabulary, checksum recipe present) and reports per-entry errors naming the file; a
broken operator entry never takes down the embedded set. Collisions: an operator entry
overrides an embedded one by name (stated policy); TWO operator files defining one name
is a load error naming both files; two tools claiming the same `tools/bin/` link name is
an install-time error naming the current holder. A platform with no entry row
fails that install with "no build for <fingerprint>" (the §14.5 fan-out then reports it
per-box). `latest` resolution failures (rate limits, offline controller) fall back to a
clear error naming the pinned alternative.

### 16.6 Implementation sketch (next build, before §14)

1. Schema + loader + validation + `catalog list`; the three kinds over internal/relay;
   unit-heavy (fixture catalogs, per-kind resolution, checksum-recipe enforcement).
2. Install path: `install tool` + `tool.install` verb + console picker + tools/bin
   linking + EnvPreamble/launcher PATH; **bash migrated** (install shell aliased,
   internal/shell resolve/installer deleted); functional on both VMs (a musl-static
   tool on musl AND glibc; agent-requested tool via the verb; idempotency).
3. Docs (README/QUICKSTART/NANA/PROTOCOL) + decision entry; curated embedded set
   finalized (bash + 2-3 tools with verified static builds).

### 16.7 Deferred, named

Runtime pin overlays (the compliance mode — likely the next data increment after usage),
agents-as-catalog-entries, the aqua-registry importer (which is also where floating
`latest` + `{version}` templating arrive), per-asset `.sha256` sidecar checksum recipes,
template sugar in `platforms`, sandbox-side tool removal/GC.

## 17. Runtime pin overlays — pinned runtime assets as data (BUILT 2026-07, decision #98)

The catalog (§16) made *utilities* data but deliberately left the language runtimes' resolvers
in Go (a resolver DSL would be code-in-YAML, #96). Runtime pins are the narrow, honest slice of
"add capabilities without writing code" that still applies to runtimes: an operator can pin the
exact **download** for a (language, version, platform) — a static url+sha — bypassing the live
upstream resolver, without anyone editing a resolver. This is the compliance / air-gapped-mirror
mode §16.7 named-deferred.

### 17.0 Scope [decided]

- Pins **augment**, they do not lock down: the resolver consults the pin table first and **falls
  through to the live resolver** on any miss. An operator pins only the versions/platforms they
  mirror; everything else resolves live as today. No global air-gap switch — incremental adoption.
- Pins cover the three managed runtimes (python, node, java). System-runtime mode (#81) is
  orthogonal (it uses the box's own binary; there's nothing to pin).
- No new operator surface: a pin is pure config, so every install path (CLI, agent verb, console
  form) picks it up unchanged — TUI/cmdline parity by construction.

### 17.1 Config shape [decided]

```yaml
runtime_pins:
  python:
    "3.11":                       # the REQUESTED version key (what the user/agent asks for)
      full: 3.11.13               # optional exact patch for the install dir; defaults to the key
      platforms:
        linux/aarch64/musl:       # os/arch/libc — the same fingerprint keys the catalog uses
          url: https://mirror.internal/cpython-3.11.13-musl.tar.gz
          sha256: 5169d922…       # MANDATORY — an unverifiable pin is rejected at load
        linux/aarch64/glibc:
          url: https://mirror.internal/cpython-3.11.13-gnu.tar.gz
          sha256: 9e399423…
```

`config.LookupRuntimePin(pins, lang, version, os, arch, libc) → (url, sha256, full, ok)` resolves
a box to its pinned asset; `ok=false` on any miss axis (lang / version / platform) → fall through.

### 17.2 The resolver seam [decided]

Each installer's `Config` gained `Pin func(version string) (relay.Pin, bool)` (nil = no pins for
this language, zero overhead). Each `resolve()` consults it as its **first** statement: a hit
returns the pinned `resolved` directly — skipping every upstream metadata call (PBS
`latest-release.json`, the nodejs index, the Adoptium API) — and a miss falls through unchanged.
`relay.Pin{FullVersion, AssetName, URL, SHA256}` maps 1:1 onto every installer's private
`resolved`, so the seam is three identical two-line short-circuits, not per-installer surgery. The
pinned asset then rides internal/relay (#90) exactly like a resolved one: sha256-verified
fetch/cache/push, so `cache list/prune` (#94) and the version-keyed install-dir idempotency/upgrade
all apply free.

### 17.3 Validation + trust

Load rejects any pinned asset missing `url` or `sha256` (the air-gap supply-chain floor, same rule
as the catalog's mandatory checksum recipe) and any platform key that isn't `os/arch/libc`. Pins
are operator-owned config that Nana can never write — an agent asks for a version, the operator's
pin table decides where the bytes come from.

### 17.4 Deferred, named

Floating/`latest` pins + `{version}` templating (arrives with the catalog's aqua-importer, §16.7),
a strict "pinned-only, no fall-through" air-gap mode (a global switch on top of the per-row pins),
pinning package-manager artifacts (pip/npm/maven already have mirror config), and sharing one pin
table across a fleet (§14).

## 18. `iceclimber sandbox` — local sandbox provisioning + the multi-sandbox registry (BUILT 2026-07, decisions #106/#107/#108)

**BUILT (v1, decision #108):** `internal/lima` (a thin `limactl` wrapper), an embedded Ubuntu vz
template (non-sudo `agent` user) + air-gap script, and the `sandbox create/list/shell/status/rm`
group. Validated live: create provisions → registers → air-gaps → bootstraps → sets the default;
the air-gap holds (direct egress blocked, DNS allowed, `agent` has no sudo to flush it); rm
destroys the VM + registry. Functional `TestSandboxLifecycle` covers it. VM-external isolation
remains the named follow-up (§18.3). The design below is as-built.


`iceclimber sandbox` is the **multi-sandbox management surface** — list / select / status / rm across
every sandbox you have, local and remote — with `create` as a thin convenience that provisions a
local one and registers it. iceclimber stays a bridge, not a VM manager: the value is the registry
+ auto-bootstrap + jump-in + (eventually) fleet, not the VM. Built now with an eye to §14 fleet.

### 18.0 Scope [decided]

- Command group: `sandbox create [name]` · `sandbox list` · `sandbox shell [name]` · `sandbox status
  [name]` · `sandbox rm [name]`. (`airgap` is not a separate verb — create applies isolation inline.)
- **Remote sandboxes are first-class** in the registry from v1: `list`/`status`/`shell`/`rm` operate on
  hand-authored/remote configs too, distinguished by the `provider:` block (below). `rm` on a remote
  only drops the registry entry — it never destroys a box iceclimber didn't create.
- Backend for `create`: **Lima** (already a dev dependency; real SSH VMs), `vmType: vz`, default distro
  **Ubuntu/glibc** (friendlier for jump-in dev; `--distro alpine` for musl). A curated Ubuntu template
  is embedded (`//go:embed`) so the product is self-contained. Provider is abstracted so containers /
  other backends can slot in later.

### 18.1 The registry — per-sandbox directory [decided]

**Base dir follows XDG** (decision #107): the state/config root moved from `~/.iceclimber/` to
`$XDG_CONFIG_HOME/iceclimber` (default `~/.config/iceclimber`), and the shared artifact cache to
`$XDG_CACHE_HOME/iceclimber` (default `~/.cache/iceclimber`) — resolved once in `internal/xdg`, with a
one-time transparent migration of an existing `~/.iceclimber/`. All paths below use the new root.

`~/.config/iceclimber/<id>/` is the registry: it already holds `config.yaml` (the `--sandbox <id>` search path),
`approvals.json`, `activity.jsonl`, `runtimes.json`, `agent.log`, and `.popo.lock`. The directory of
subdirs IS the sandbox list; `sandbox list` scans `~/.config/iceclimber/*/config.yaml`. Chosen over a single
`~/.config/iceclimber/config.yaml` with a `sandboxes:` map (the §14.1 sketch) because per-dir is MORE
fleet-native: no shared-file write contention when N sandboxes are managed concurrently, and each
sandbox's config + state + lock already co-locate. The single-file `defaults: + sandboxes:` map stays
supported as an operator-authored ADDITIONAL source, merged at list/select time — parked for the fleet
build, not precluded. `sandbox_id` must equal the dir name.

- **`provider:` block** (new, optional, in `config.yaml`): `{type: lima, instance: iceclimber-<id>,
  distro: ubuntu, arch: arm64}`. Present ⇒ iceclimber-managed local VM (so `rm`/`status` manage the
  underlying VM). Absent ⇒ remote/unmanaged (config-only; `rm` just forgets it).
- **Default pointer** `~/.config/iceclimber/default` (a file naming the default id): `iceclimber shell` /
  commands with no `--sandbox` and no `iceclimber.yaml` fall back to it. First-created wins; `--default`
  reassigns. Extends today's config resolution (no-config → `iceclimber.yaml` in cwd → registry default).

### 18.2 create flow + auto-serve [decided]

`sandbox create dev`: `limactl start` the embedded Ubuntu template as `iceclimber-dev` → read its SSH
details (127.0.0.1:port, lima user, identity — the pattern the functional harness already uses) → write
`~/.config/iceclimber/dev/config.yaml` (`sandbox_id: dev`, `egress_mode: proxy`, the `provider:` block) → apply
egress isolation (§18.3) → `bootstrap` (tree + popo, proxy-mode trust). Defaults: 2 CPU / 4 GiB / 20 GiB
(flags); bootstrap on; agent off (`--agent claude`); drop-into-shell off (print the hints) unless
`--shell`.

- **Auto-serve** [decided]: because proxy egress only works while `serve` runs, `sandbox shell` and
  `create --shell` **start a background `serve` for the session** and drop you in — so egress works
  through the proxy while you're in the box — then stop `serve` on exit (`--serve` keeps it up). This is
  what makes an air-gapped box a smooth "jump in and start developing" experience.

### 18.3 Egress isolation — a pluggable SEAM [decided], VM-external deferred [named]

Air-gap-by-default, but the enforcement is a **pluggable isolation step** so the mechanism can strengthen
without reworking the feature. **v1 mechanism (workload-external):** the egress firewall is applied
**by root at first boot** (cloud-init) and the agent/workload runs as a **non-root user without sudo**, so
the workload can't flush it. This is honest but NOT strictly VM-external (a guest with root could bypass).

**The allow-list is "nothing out EXCEPT the agent's own LLM API" (decision #109), not "nothing out."**
A Claude agent running IN the box must reach its model directly — its streaming/TLS control channel is
the ONE thing Popo does NOT bridge (MITM'ing it would break it), exactly as the demo firewall allows.
So the air-gap permits 443 to Anthropic's published ingress ranges + DNS + loopback + established, and
DROPs everything else (packages/web/runtimes ride Popo's reverse-tunnel proxy). An earlier draft blocked
the API too — a bug caught in review: it would have left a box that literally can't run an agent.

**VM-external (the desired end state) — deferred pending validation.** Determination from Lima 2.1.2 (vz):
Lima ALWAYS provisions a built-in internet-capable user-mode network for SSH; a `socket_vmnet` network in
`networks:` is ADDITIVE, so it can't remove that internet path — and the built-in net's egress is
unfilterable host-process traffic, so a host `pf` rule on a vmnet subnet **leaks**. The only real
VM-external path is DISABLING the built-in net entirely and running SSH-only over a `socket_vmnet`
**host-only** network (no internet by construction) — whether Lima will do that on vz is undocumented +
**unverified**. It also carries real cost here: Lima is Nix-installed on the dev machine, so `socket_vmnet`
is a nix-darwin change + a `limactl sudoers` entry. So VM-external is a named follow-up: validate the
"SSH-only, built-in net disabled, host-only vmnet" config empirically, and if it holds, drop it into the
isolation seam. iceclimber's proxy egress needs NO guest internet (egress rides the SSH reverse tunnel),
so the target — "SSH in, nothing out except the agent's LLM API" — is well-defined; only the Lima
mechanism is open.

### 18.4 Fleet forward-compat [decided]

Everything composes toward §14: the per-dir registry is exactly what `--sandbox all`/globs enumerate; the
`provider:` block generalizes to N backends; the default pointer becomes the fleet's default target; and
remote sandboxes being first-class means `sandbox` is the fleet management surface from day one, seeded by
local-create. The single-file `defaults: + sandboxes:` map (§14.1) merges in later as an operator-authored
source without changing the registry model.

### 18.5 v1 vs deferred

- **v1:** `create` (Lima/Ubuntu) · `list` · `shell` (auto-serve) · `status` · `rm`; per-dir registry +
  `provider:` block + default pointer; remote sandboxes first-class; air-gap via the workload-external
  seam; a functional test that creates → bootstraps → jumps-in → tears-down a real Lima box.
- **Deferred, named:** VM-external isolation (socket_vmnet host-only, validated); Alpine/musl create path
  (template exists in tests); container backends; the single-file fleet config merge; `sandbox` fleet
  fan-out (§14).
